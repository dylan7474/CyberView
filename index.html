Backup & Restore

1. Back up

Downloads everything in the portal (register, review queue, risk acceptances, vulnerability figures) as one JSON file. Keep it somewhere safe.

2. Restore

Replaces all the data with a backup file made above. You see what is in the file first, and a backup of the current data is downloaded before anything is replaced.

Restoring is for administrators. You are signed in as . Ask an administrator to restore, or have one change your role on the Users page.

3. Start again (wipe everything)

Deletes all the data in the portal. Download a backup first. You are asked to confirm.

On the server itself

The database is also dumped on the server with ./deploy.sh backup (files in backups/) and loaded back with ./deploy.sh restore backups/FILE.sql.gz. Use that for a nightly copy or if the portal will not start.

Risk model

The scoring behind the ⚖️ Risk Report: a weighted component score per finding (observed exploitation, asset criticality, exposure, EPSS, CVSS) times a Service Tier multiplier, with contextual modifiers. The defaults are industry-standard (the README spec); change them to suit your organisation. This never changes the P1–P4 action engine or the team Status.

    How this is scored. The same rules and rankings as Vuln Management, Status and Patch Plan. Each open finding gets an action priority P1-P4 from its finding tier and its asset's Tier (set by people; not set counts as Tier 2), with Internet-facing assets more urgent, and a due date counted from when it was first found (findings from before go-live are backlog with their own targets). The exact rules, days and tier names in use are in Organisation setup (Status rules and Organisation). Assets rank by worst priority, then Tier, then TruRisk (0-1000; Low <500, Medium 500-699, High 700-849, Critical 850+). TruRisk is one score per asset, so it is never added up across findings. Finding tiers come from Qualys signals: Fix now = CISA KEV, active attacks, ransomware, wormable or zero-day; This sprint = QVS 70+ or remote code execution with a public exploit; Scheduled = severity 5 or QVS 40+; otherwise Routine. An EPSS (FIRST) score at or above the Status-rules threshold moves a finding one tier up, and a CVE on the CISA KEV list counts as known-exploited even without a Qualys flag. Fixes are grouped by QID and ranked by priority, then assets affected × QVS.

    Where this comes from. Dates: your table (section 6) first, then endoflife.date (API v1; on a server, fetched by the server every day and kept in the database; otherwise fetched by this browser and kept a week). Security fixes end is the vendor's end of security updates (Microsoft extended support, Red Hat maintenance, VMware general support); mainstream is the end of first-level support. Status counts from today: Unsupported = that date has passed or Qualys says EOL/EOS (no security fixes) for the release, which catches RHEL minor releases that endoflife.date lists only by major version. The Qualys lifecycle stage (asset export, Operating System Lifecycle Stage) is shown next to each asset. Hardware: EOS = end of sale; OBS = obsolete, no support. End-of-life software is every scan detection whose Qualys title starts “EOL/Obsolete”, so it only covers assets in the imported vulnerability exports.
